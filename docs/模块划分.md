# Pegboard 模块划分文档

## 1. 模块清单

| 模块 | 层 | 一句话职责 |
|---|---|---|
| config | 基础 | 加载与校验配置 |
| app | 基础 | 应用识别、清单、生命周期 |
| identity | 接入 | 解析不透明 subject |
| ingress | 接入 | 路由、请求上下文、同源约束 |
| guard | 治理 | 权限、限额、SSRF、审计 |
| statics | 托管 | 应用产物托管 |
| store | 能力 | KV 原语 |
| files | 能力 | Blob 原语与签名 |
| proxy | 能力 | HTTP/WS/SSE 转发 |
| sdk | 能力 | 注入前端的 SDK |
| admin | 管理 | 宿主元数据可视化 |
| audit | 治理 | 日志与事件记录 |

依赖方向严格单向：基础 ← 接入 ← 治理 ← 能力 ← 存储。禁止反向依赖。

## 2. 基础模块

### config
- **职责**：加载配置文件与环境变量，产出只读配置。
- **对外**：`Config`（监听、模式、身份来源、限额默认、存储根）。
- **依赖**：无。
- **边界**：不做运行时热更新；不感知应用。

### app
- **职责**：扫描应用目录，解析清单，维护应用注册表；安装/卸载/启停。
- **对外**：`AppRegistry`，按 id 查询 `AppMeta`（清单、路径、权限、限额）。
- **依赖**：config。
- **内部**：清单解析 + 校验；目录与元数据分离。
- **边界**：不承载业务语义；不做版本发布。

## 3. 接入模块

### identity
- **职责**：把请求映射为不透明 subject（可为空）。
- **对外**：`resolve(req) -> Option<Subject>`。
- **依赖**：config。
- **内部**：三种来源策略（固定 / 反代头 / token），可配置。
- **边界**：不建用户表、不做角色、不做登录。

### ingress
- **职责**：路由分发、构造请求上下文（app、subject、来源）、同源约束。
- **对外**：`RequestContext`，交给下游模块。
- **依赖**：app、identity、config。
- **内部**：路由表；上下文注入；拒绝跨应用访问。
- **边界**：不做权限判定；不做业务处理。

## 4. 治理模块

### guard
- **职责**：基于清单校验权限与限额；SSRF 防护；响应头清理。
- **对外**：`check(ctx, action) -> Result`；`sanitize(headers)`。
- **依赖**：app、config、audit。
- **内部**：权限白名单、限额计数器、目标地址校验、逐跳重定向校验。
- **边界**：不做授权决策（那是应用的事）；不感知业务数据。

### audit
- **职责**：记录访问与错误事件；提供查询。
- **对外**：`record(event)`；`query(filter)`。
- **依赖**：config。
- **内部**：结构化日志 + 环形缓冲/文件。
- **边界**：不存业务数据；不做告警。

## 5. 能力模块

### statics
- **职责**：托管应用产物，处理 SPA 回退、MIME、缓存、Range。
- **对外**：`serve(app_id, path) -> Response`。
- **依赖**：app。
- **边界**：不经过 guard；不处理 API 路由。

### store
- **职责**：KV 原语，按应用隔离。
- **对外**：`get/set/delete/list/batch`，键空间由应用决定。
- **依赖**：app、config。
- **内部**：每应用独立库；配额执行。
- **边界**：不解释键语义；不做跨应用查询。

### files
- **职责**：Blob 读写、Range、列表、签名访问。
- **对外**：`upload/get/delete/list/sign`。
- **依赖**：app、config、audit。
- **内部**：流式落盘；元数据与内容分离；签名 token 由宿主维护。
- **边界**：不做授权决策；签名只回答“有效吗”，不回答“谁能看”。

### proxy
- **职责**：HTTP/WS/SSE 转发；资源代理地址；fetch 兜底注入。
- **对外**：`forward(req)`；`connect_ws(url)`；`asset_url(url)`。
- **依赖**：guard、config。
- **内部**：请求重写、流式透传、重定向处理、二进制安全。
- **边界**：不做系统级代理、不做 MITM、不缓存业务响应。

### sdk
- **职责**：提供注入前端的 SDK 与类型。
- **对外**：`sdk.js`、`sdk.d.ts`、示例。
- **依赖**：无（仅浏览器侧）。
- **内部**：`host` 命名空间；fetch shim。
- **边界**：不暴露宿主内部结构；不绕过 guard。

## 6. 管理模块

### admin
- **职责**：应用列表、权限、限额、日志的可视化与操作。
- **对外**：Web 页面 + 管理 API。
- **依赖**：app、audit、config。
- **内部**：只读为主，操作限于宿主元数据。
- **边界**：不介入应用数据；不做应用商店。

## 7. 模块交互

```
请求 → ingress ──▶ statics
              │
              ├──▶ guard ──▶ store / files / proxy
              │       │
              │       └──▶ audit
              └──▶ identity
```

- 静态路径：ingress → statics，绕过 guard。
- 能力路径：ingress → guard → 能力模块。
- 签名路径：ingress → files（校验 token），跳过 identity。

## 8. 扩展点

| 扩展 | 方式 |
|---|---|
| 新增能力 | 新模块 + 注册到 ingress 路由 + 清单权限字段 |
| 新增身份来源 | identity 增加策略，不改下游 |
| 替换存储实现 | store/files 接口不变，替换内部 |
| 新增治理规则 | guard 增加策略，不侵入能力模块 |
| 后台任务/事件推送 | 独立模块，走 guard，不改现有层 |

## 9. 模块级验收

| 模块 | 验收 |
|---|---|
| ingress | 跨应用请求被拒 |
| identity | 三种来源可切换，应用无感 |
| guard | 越权目标被拒且错误可读 |
| store/files | 应用间不可互访 |
| proxy | 流式首字节与直连相当 |
| statics | 同事通过 URL 可访问 |
| audit | 可追溯谁在何时访问了什么 |

## 10. 边界（模块层不做）

- 无用户模块、无角色、无会话。
- 无业务模型、无授权决策。
- 无系统级代理、无 MITM。
- 无应用商店、无发布审核。
- 无跨应用数据聚合。
