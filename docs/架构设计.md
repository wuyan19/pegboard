# Pegboard 架构设计文档

## 1. 定位

薄宿主，托管 AI 生成的 HTML 应用。宿主提供浏览器不具备的能力与边界；应用拥有全部业务语义。

## 2. 架构原则

- **薄宿主**：宿主只做浏览器做不到的事。任何可下沉到应用的能力，不下沉到宿主。
- **能力与语义分离**：宿主给原语，应用给含义。
- **单向依赖**：应用依赖宿主能力；宿主不感知应用业务。
- **强制隔离**：应用之间数据不可互访，由宿主保证，非应用自律。
- **边界即设计**：权限、限额、SSRF 防护是一等能力，非事后补丁。
- **稳定面**：对外能力面（SDK/HTTP）优先稳定；内部实现可替换。

## 3. 系统总览

```
                    ┌─────────────────────────────┐
   Browser ───────▶ │  Pegboard Host (Rust)       │
   (主入口)         │                             │
                    │  ┌─────────┐  ┌──────────┐  │
                    │  │ 静态托管 │  │ 能力层    │  │
                    │  └─────────┘  │ store    │  │
   Tauri/Wry ─────▶ │               │ files    │  │
   (可选壳)         │               │ proxy    │  │
                    │               │ user?    │  │
                    │               └──────────┘  │
                    │  ┌─────────┐  ┌──────────┐  │
                    │  │ 治理层   │  │ 管理页    │  │
                    │  │权限/限额 │  │ /admin   │  │
                    │  │日志/审计 │  └──────────┘  │
                    │  └─────────┘                │
                    └──────────┬──────────────────┘
                               │
                     ┌─────────┴─────────┐
                     │ data/apps_data/   │
                     │   <id>/: app.db   │
                     │         files/    │
                     └───────────────────┘
```

宿主是唯一进程，对外是 HTTP 服务。浏览器为主入口，桌面壳可选。

## 4. 分层与职责

| 层 | 职责 | 不负责 |
|---|---|---|
| 接入层 | 路由、鉴权、应用识别、同源约束 | 业务逻辑 |
| 静态托管 | 托管应用产物、SPA 回退、缓存、Range | 构建 |
| 能力层 | store / files / proxy / user 原语 | 业务语义、授权决策 |
| 治理层 | 权限校验、限额、SSRF 防护、日志、审计 | 用户模型 |
| 存储层 | 按应用隔离的 KV、Blob、元数据 | 跨应用查询 |
| 管理层 | 应用列表、权限查看、日志 | 应用商店 |

依赖方向（全文档唯一表述）：基础（config、app）最底；audit 为叶子，任何层可调；guard 只依赖基础与 audit；store/files/proxy 依赖基础，proxy 另复用 guard 校验目标；ingress 编排治理与能力。反向依赖不存在。

## 5. 组件

**接入层**
- 识别当前应用（路径或请求头），建立请求上下文。
- 校验调用者（可选 token / 反代注入），生成不透明 subject。
- 拒绝跨应用访问。

**静态托管**
- 按应用路由到其产物目录，支持单文件与 dist。
- 提供 SPA 回退、正确 MIME、缓存与 Range。
- 静态资源不经过治理层，直出。

**能力层**
- `store`：KV 原语，键空间由应用决定。
- `files`：Blob 读写、Range、列表、签名访问。
- `proxy`：HTTP/WS/SSE 转发、资源代理地址、fetch 兜底。
- `user`：仅暴露不透明 subject，可为空。

**治理层**
- 加载应用清单，校验权限与限额。
- SSRF 防护：内网、本机、云元数据默认拒绝，白名单逐跳校验。
- 响应头清理、超时、重定向限制、响应大小上限。
- 记录访问与错误，支持审计。

**存储层**
- 每个应用独立 KV 库与文件目录。
- 签名 token 与元数据由宿主维护，与应用数据分离。
- 配额在此层强制执行。

**管理层**
- 应用列表（含未安装候选）、权限、限额、用量、日志的可视化。
- 应用生命周期操作：安装/卸载/删除/启停；仅操作宿主元数据，不介入应用数据语义。

## 6. 关键数据流

**静态访问**
Browser → 接入层（识别应用）→ 静态托管 → 产物。

**能力调用**
App → 接入层（识别应用 + subject）→ 治理层（权限 + 限额）→ 能力层 → 存储层。

**代理调用**
App → 接入层 → 治理层（白名单 + SSRF + 限额）→ 能力层（转发）→ 目标。
流式响应全程透传，不缓冲。

**签名访问**
App 请求签名 → 能力层签发 token → 外部访问带 token 的 URL → 能力层校验 token（files，存取经 app 模块接口），跳过调用者鉴权。

## 7. 关键决策

| 决策 | 理由 |
|---|---|
| 单进程宿主 + 浏览器主入口 | 部署最简，同事通过 URL 即可用；桌面壳非必需 |
| 应用隔离用物理隔离（独立库/目录） | 不依赖应用自律，失败模式清晰 |
| 跨域下沉到宿主代理 | 浏览器无法解决；应用不写 CORS 代码 |
| fetch 兜底 + 显式 SDK 双轨 | 兼容 AI 惯用写法，同时保留可审计路径 |
| subject 不透明、可选 | 宿主不做用户系统，避免重造框架 |
| 权限与限额由清单声明 | 稳定、可审计、AI 可读 |
| 宿主不缓存业务响应 | 避免语义泄漏与一致性问题 |
| 进程管理（托盘/启动模式/自升级）独立于能力面 | 属进程编排，不进 HTTP 能力面与 SDK |

## 8. 演进方向

- 能力面只增不改，新增能力不破坏既有应用。
- 反代注入、token、固定 subject 三种身份来源并存，切换不改应用。
- 后台任务与事件推送作为独立能力层扩展，不侵入现有层。
- 存储层可替换实现，接口不变。

## 9. 边界（架构不做）

- 不做系统级代理、HTTPS 中间人。
- 不做登录、用户表、角色、会话。
- 不做应用商店、发布、审核。
- 不做业务数据模型与授权决策。
- 不做跨应用数据聚合。

## 10. 验收对应

| 需求 | 架构保障 |
|---|---|
| 应用免改 CORS 运行 | 代理 + fetch 兜底 |
| 应用间数据不可见 | 物理隔离 + 接入层识别 |
| 越权目标被拒且错误可读 | 治理层统一错误 |
| 流式首字节与直连相当 | 能力层透传不缓冲 |
| 同事 URL 可访问 | 浏览器主入口 + 可选身份来源 |

## 11. 进程形态与在线升级（M8）

宿主仍是唯一服务进程，本节只约定**进程编排**，不新增能力面。

**启动模式**（同一二进制，行为随启动环境）：

| 形态 | 判定 | 行为 |
|---|---|---|
| CLI / 终端 | stdout 为 TTY | 终端横幅 + 日志；Ctrl+C/SIGTERM 优雅退出；默认尝试托盘 |
| 无终端（双击 .app / `open` / 开机自启） | stdout 非 TTY | 无横幅；运行日志落 `logs/host.log`；托盘常驻 |
| 无头（`--no-tray` / ssh / 无 GUI 会话） | 显式或托盘初始化失败 | 纯服务进程，信号退出；托盘失败自动降级，不影响服务可用性 |

**线程模型**：托盘事件循环（tao/tray-icon）必须在主线程（macOS NSApplication 约束）；tokio 运行时与 axum 跑在子线程。托盘 ↔ 服务经两个通道协调：服务端 `ProcessControl` trait（cli 侧实现：托盘模式转发事件循环，无头模式直接 spawn）触发重启；托盘退出/重启时通知服务优雅关闭，并等待「服务已停止」标志（含 10s 超时兜底）再结束进程，保证审计落盘。

**重启协议**：新进程以相同参数 spawn，携带 `PEGBOARD_RESTART_CHILD=1` 换得最长 ~2.5s 的端口绑定重试窗口（等待旧进程释放监听）；旧进程随后优雅退出。

**在线升级**（信任锚是**签名**而非更新源 URL）：

```
检查：manifest_url → {payload, signature} 信封 → minisign(Ed25519) 验签（编译期内嵌公钥）
      → 版本比较（semver，坏版本号按「不新」处理）
下载：流式落盘（data_root/tmp），边下边算 sha256，超声明大小即中止
安装：sha256 + 资产签名双校验通过后——
      Windows/Linux：self-replace 原子替换二进制
      macOS：整包替换 .app（staging → backup → rename → 失败回滚），只换内部二进制会使
             ad-hoc 签名失效且 Info.plist 版本过期
重启：restart_pending → 管理页/托盘触发 host/restart → 新版本接管端口与数据
```

- 仅手动触发（管理页按钮），不自动轮询、不静默安装。
- 更新源 URL 可配置（`[update] manifest_url`，缺省关闭），但内容必须通过内嵌公钥验签——URL 只决定去哪取，签名决定信不信。
- 更新属于宿主自身维护，不经过治理层/能力层；应用数据与 host.db 不受升级影响（数据目录与产物目录布局不变）。
