# 里程碑简报

按实施文档推进过程中的记录：做了什么、验收结果、文档是否变更、骨架文档冲突点。

## M1：配置与应用扫描

**做了什么**
- 1.1 `config`：加载（默认→文件→`PEGBOARD_` 环境变量）+ 校验（Lan 身份匹配、限额自洽、forwarded 非空）。
- 1.2 `app`：清单解析、id/entry 路径安全（canonicalize + 前缀校验）、限额只能收紧、扫描容错（坏应用进 warnings 不阻塞）。
- 1.3 `audit`：有界通道 + 后台线程串行落盘、按大小滚动、非阻塞 record（满则丢弃计数）、查询过滤。
- 1.4 CLI：clap 参数（--config/--listen/--apps-dir/--data-root/--check/--log）、覆盖项、check 退出码 0/1/2。
- 1.5 集成测试：cli/tests/check.rs 驱动真实二进制（坏应用不阻塞好应用）。
- 附带 fixture：apps/demo（M2 静态托管测试用）。

**验收结果**
- `cargo test -p pegboard-core`（config/app/audit 三组）42 通过 ✅
- `cargo run -p pegboard-cli -- --check` 输出应用列表、退出码 0 ✅（demo 应用实测）
- fmt / clippy -D warnings / check-deps.sh 全绿 ✅

**文档变更（骨架文档冲突，以主文档为准）**
- `config` 骨架缺 `[storage] apps_dir`——主文档 config.example.toml 与架构图均含产物/数据目录分离，已按主文档实现（StorageConfig 含 apps_dir）。
- `app` 骨架 `LimitsOverride` 键名为 store_bytes 等——主文档（API契约 §2、数据模型 §8）限额键为 kv_value_bytes / kv_total_bytes / file_bytes / file_total_bytes / net_rps 五键，与 config 完全一致，已按主文档实现。
- `app` 骨架 `scan` 返回 `Result<Self, Vec<AppError>>` 无法表达「成功 + 告警」并存，改为 `Result<ScanOutcome, AppError>`（ScanOutcome 含 registry + warnings）；Err 仅 apps 目录不可读。
- `app` 骨架 `reload_one` 返回 `&AppMeta` 需要内部 expect，改为返回 `AppMeta`。

## M2：HTTP 服务与静态托管

**做了什么**
- 2.1 ingress 骨架：AppState（config/apps/auditor）、build_router、契约化 404 fallback；错误体 `{error:{code,message,detail}}`。
- 2.2 statics：手写文件服务（tokio::fs + ReaderStream），Range 单范围 206/416、SPA 回退（无扩展名→entry）、ETag/Last-Modified/304、缓存分级（hash 资源 immutable）、路径 canonicalize + 前缀校验；text/html 注入 `__PEGBOARD__` 引导 + `/sdk.js`（合法 JSON，shim 按清单；带 Range 时不注入以保字节偏移）。
- 2.3 SDK 占位：pegboard-sdk crate 内嵌 assets/sdk.js 与 sdk.d.ts（include_str!），`/sdk.js`、`/sdk.d.ts` 返回 200。
- 2.4 CLI serve：runtime 装配（数据目录→注册表→审计→状态→路由→监听）+ shutdown 信号（SIGINT/SIGTERM）+ 优雅排空（10s 上限）+ 审计 spawn_blocking 落盘。
- 2.5 集成测试：cli/tests/serve.rs 真实二进制起停（端口 0 + 日志解析地址、SIGTERM 优雅退出、坏应用不阻塞启动）。
- 前置重构：AppRegistry 存 `Arc<AppMeta>`（读锁短持有、不跨 await）；Auditor 拆出可克隆 AuditorHandle 供 AppState 共享。

**验收结果**
- statics 24 项（Range/SPA/回退/缓存/方法/安全/SDK）✅；契约 8 项（404/400/错误体形状/注入）✅；cli serve 3 项 ✅；core 42 项回归 ✅
- fmt / clippy -D warnings / check-deps.sh 全绿 ✅
- 手工冒烟：浏览器视角 curl 验证 index 注入、sdk.js 200、SPA 200、APP_NOT_FOUND 错误体、SIGTERM 后 exit 0 且日志含 listening/stopped ✅

**文档变更**
- `Cargo.toml冻结.md` + server Cargo.toml：axum 需加 `http1`/`tokio`/`json` 特性（default-features=false 下 `axum::serve` 与 Json extractor 必需），与 clap std 同类笔误级修正。
- 设计偏差记录（非冲突）：静态路由使用 axum 0.8 新路径语法 `/apps/{app_id}/{*path}`；`/apps/{id}/` 空通配不匹配，需显式路由。

## M3：Store

**做了什么**
- 3.1 `store`（core）：AppStore（WAL + kv 表 + 迁移）、配额写入前执行（单值/总量，覆盖写按增量）、前缀 LIKE 转义、批量事务原子、StoreManager 惰性打开 + 按应用隔离 + 清单收紧后重开。
- 3.2 Store handler（server/ingress/store_api.rs）：GET/PUT/DELETE /api/store/kv/{*key}、GET /api/store/kv?prefix=、POST /api/store/kv/batch；spawn_blocking 包装同步 core；trace_audit 统一审计。
- 3.3 `identity`（core）：Fixed/Forwarded/Tokens 三策略、bearer 大小写不敏感、token 常量时间比较、X-Forwarded-User 信任 peer + 长度上限。
- 3.4 ingress 接入：RequestContext extractor（X-Pegboard-App 识别 app → identity 解析 subject）；错误映射集中 ingress/error.rs（GuardError/StoreError → 契约错误码）。
- 3.5 `guard` 能力部分：check_capability（store/files 布尔、net/ws 非空清单）。
- 3.6 SDK host.store：apiFetch（X-Pegboard-App 头、HostError 结构化）、get/set/delete/list/batch；key 按 %2F 编码。sdk.d.ts 补 store 类型。
- 场景测试（cli/tests/scenarios.rs）：node 桥接执行真实 sdk.js 打真实服务器（roundtrip/list/batch/delete/HostError），M7 换 Playwright。

**验收结果**
- core 80 项（store 19 + identity 13 + guard 4 + 回归）✅；契约 20 项（403/404/400/413/隔离/%2F）✅；场景 2 项 ✅；fmt / clippy / deps 全绿 ✅

**文档变更（骨架冲突，以主文档为准）**
- store 骨架数据根为 `<data_root>/apps/`——主文档（数据模型 §1）为 `apps_data/`，已按主文档实现。
- guard 骨架限流说明「store/files 暂用同一上限」——主文档（数据模型 §8）net_rps 只作用网络能力，store/files 不限频，按主文档执行。
- 决策记录：identity 失败映射 PERMISSION_DENIED+401（API契约 §6「401 仅在 token 身份来源凭证缺失/无效时出现」；v1 fixed 模式不触发）。StoreError::Open/Io 归一 UPSTREAM_ERROR 502（契约无 INTERNAL 码）。
- `Cargo.toml冻结.md`：axum 增补 `query` 特性（Query extractor 必需）。

## M4：Proxy

**做了什么**
- 4.1 guard 白名单 + SSRF：origin/URL 前缀匹配（端口归一、路径区分）、私网/保留地址判定（含 CGNAT/ULA/链路本地/云元数据）、显式本地例外（IP 字面量或 localhost 白名单）、域名经 tokio 异步解析后校验。
- 4.2 guard 限流：(app_id, action) 固定 1s 窗口、可注入时钟（窗口复位测试）、仅网络能力调用。
- guard.sanitize 双向头清理：出站剥 Cookie/Host/X-Forwarded-*/身份注入头/逐跳头（保留 Authorization/Origin/Referer）；入站剥 Set-Cookie/Access-Control-*/CSP/HSTS 等。
- 4.3 proxy 模块：forward（逐跳重定向重校验、301/302/303→GET、流式判定 SSE/chunked/未知长度透传、已知长度超限 TooLarge、连接+读超时无总超时）、asset_url；raw-HTTP mock 测试（含 chunked 解码）。
- 4.4 Proxy/Asset handler：/api/proxy（任意方法、请求体流转发生不缓冲）、/api/asset（GET）；ProxyError 集中映射（RedirectDenied→403、Timeout→504、TooLarge→413）。
- 4.5 SDK：host.fetch（同源原生/跨域代理、非 2xx → HostError、X-Pegboard-App 注入）、host.url（/api/asset）、fetch shim（含 Request 对象展开补身份头）。
- 4.6 SSE 场景：node SSE 上游（100ms×20 事件）经代理 vs 直连——事件数一致、首字节延迟 delta < 500ms 且 < 1.5s（证明未整流缓冲）。

**验收结果**
- core 107 项（guard 白名单/SSRF/限流/sanitize + proxy 11 项）✅；proxy 契约 12 项（403/400/429/重定向/头清理/SSE 透传）✅；场景 4 项（fetch/shim/url/TARGET_DENIED/SSE 首字节）✅；fmt / clippy / deps 全绿 ✅

**文档变更（骨架冲突，以主文档为准）**
- proxy 骨架出站「保留 Cookie 透传」——主文档（API契约 §5 定稿）出站剥离 Cookie（对齐原生 fetch 默认不携环境 cookie），已按主文档。
- proxy 骨架 `build_client` 用 expect——违反红线，改为返回 Result。
- proxy 骨架 ProxyConfig.timeout（总超时）会杀死 SSE 长流——改为 connect_timeout + read_timeout（读停滞保护），无总超时；记录为设计修正。
- 骨架流式判定「Content-Length > max → 流式透传」与骨架自身测试（断言 TooLarge）矛盾——按测试语义实现：已知长度超上限即 TooLarge，未知长度/chunked/SSE 才透传。
- `Cargo.toml冻结.md`：server 增 url 依赖（proxy handler 解析目标）；cli dev-deps 增 futures-util/url、reqwest 增 stream（场景测试）。
- 307/308 携流式体的重定向不可重放 → RedirectWithBody 错误（502），记录为边界行为。
